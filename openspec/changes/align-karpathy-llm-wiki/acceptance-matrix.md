# Runtime acceptance matrix

Status: acceptance criteria only; no scenario in this document is asserted to have passed. The implementation baseline used to prepare this inventory is `172d0e5`. Executed evidence belongs in `verification.md`, bound to the exact reviewed commit and environment.

## Scope and authority

The source of requirements is [the core design](../../../docs/design/llm-wiki-core.md), [this change's scenarios](specs/llm-wiki/spec.md), [implementation tasks](tasks.md), [the README](../../../README.md), and the existing [transaction](../../specs/transactional-vault/spec.md), [access](../../specs/memory-access-control/spec.md), [retrieval](../../specs/hybrid-memory-index/spec.md), [agent API](../../specs/production-agent-api/spec.md), [maintenance](../../specs/maintenance-service/spec.md), and [remote sync](../../specs/remote-git-sync/spec.md) contracts. This matrix expands those promises into observable tests; it does not replace them or narrow implementation to the easiest successful fixture.

Required new capabilities are persistent source/entity/concept/synthesis/comparison/query pages, operational purpose and rules, incremental atomic compilation, classified navigation, catalog-first answers with explicit filing, structural and semantic lint with separately authorized repair, and consistent CLI/MCP/Harness access. Existing atomic-memory workflows remain part of the retention set.

The document scan found no additional distinct, explicitly unfinished feature outside this Wiki change. The completed `close-independent-audit-findings` tasks remain retention obligations. Its unverified Windows process-tree behavior, production credentials/remotes, and power-loss durability are evidence limitations, not newly promised features. The README explicitly excludes a browser editor, hosted control plane, multi-tenant database, distributed writer consensus, and automatic semantic conflict adjudication; this change does not silently add them.

## Evidence conventions

Every implementation test should identify its matrix ID. Record actual test path/name, command, exit status, commit, runtime, platform, default Git branch, and any skipped dependency in `verification.md`. Proposed test descriptions below are requirements for evidence, not claims that test files already exist.

| Evidence | What it establishes | What it does not establish |
| --- | --- | --- |
| `D` — deterministic integration | Real temporary vault, canonical Markdown/envelopes, actual Git history, public vault API, controlled proposed model output, and independent assertions over resulting files | A fake provider returning a prepared plan does not prove prompt serialization, HTTP parsing, provider limits, or model reasoning |
| `P` — provider-protocol integration | The real OpenAI-compatible provider calls a local HTTP fixture server; the server captures actual requests and returns protocol-shaped responses, malformed responses, failures, delays, and oversized streams | A local HTTP fixture is still a simulated service; it does not prove a hosted model follows instructions or produces good synthesis |
| `L` — live model observation | If credentials are available and authorized, record provider/model, sanitized input/output, cited versions, observed artifacts, and a semantic rubric for the two-source corpus | One successful live run does not prove general reliability; do not report this as run when only `D` or `P` executed |
| `A` — adapter/installed-package integration | Spawn the built CLI, negotiate/call a real MCP server, execute official Harness tools, and install the produced package into an independent consumer | Checking schema declarations or calling a mocked registration callback alone does not establish actual adapter behavior |
| `R` — retained and independent evidence | Run existing assertions unchanged, inspect committed artifacts and original requirements in an isolated read-only review | Passing the old suite alone is not proof of new Wiki functionality; a review that inherits the proposer's private rationale is not independent |

The required deterministic and protocol gates must pass even without a hosted model account. If `L` cannot run, report that exact limitation and avoid claiming hosted-model semantic quality was verified. Provider input assertions must inspect actual captured request bodies rather than only a helper's intended arguments. Crash/atomicity assertions must reread filesystem and Git state from a fresh vault/process rather than trusting a returned success object.

## Shared executable fixtures

Use a fresh vault per scenario and deterministic time where expiry is relevant. Record bytes/hashes of every evidence file and a canonical snapshot consisting of managed paths and bytes, shadow Git HEAD, page revisions, catalog, and chronological log. Runtime counters/caches may change only where the operation contract allows; they never count as canonical knowledge.

- `E1`: AtlasStore supports daily snapshots for project deployments; retain its stated condition and verification date.
- `E2`: AtlasStore supports restoration to a separate instance, with a documented limitation. The facts complement `E1` and require a shared entity page plus synthesis.
- `E3`: A separately dated source contradicts one scoped claim from `E1`; its authority is not assumed to supersede `E1`.
- `E4`: A source compares AtlasStore with another system and introduces a concept. It exercises comparison and concept pages without converting them into isolated statement cards.
- `S`: Restricted evidence, page title, logical key, source URI, rule/purpose text, and body each contain separate unmistakable secret canaries. Include a public visible neighbor and a derived-page dependency chain.
- Principals: read-only, write-only, review-only, maintain-only, authorized combined roles, wrong tenant, missing tenant, scope-limited, and clearance-limited. Identity is configured outside tool arguments.

The model fixture may name expected pages, but assertions must independently read their persisted bodies, source references, links, restrictions, revisions, catalog entries, and Git attribution. Do not pass a test merely because the system echoes a prepared plan.

## Completion record

Before marking implementation tasks complete, `verification.md` must map every matrix ID to actual evidence or an explicit unresolved limitation and name the final independently reviewed local commit. A feature being callable is not sufficient when its negative-path or retention criteria fail. Full implementation acceptance requires no unresolved confirmed missing capability or defect within the documented scope, all mandatory executable gates, and an isolated review of the final candidate. Finite tests and review do not establish the absence of unknown defects.
