# Design

Require read/write permission before preparation and an explicit current expected revision. Re-read the historical page and its graph through the bounded local revision-view reader, with current authority, tenant, opt-in, lifecycle and encryption checks. Never accept a caller-supplied snapshot as evidence. Author a new body/summary and optionally title; ordinary memories remain on their separate review path.

The signed merge plan records the source commit, base target hash/revision, historical support keys and strict inherited boundary (scope, sensitivity, conditions, uncertainty, conflict status and earliest expiration). Historical ordinary-memory effective conditions also travel with the proposal. Both historical and current sources remain immutable and attached. Compilation rules and the current visible catalog retain their normal conservative influence. Merge does not resolve an existing or historical conflict or lengthen an expiration.

The confidential-selection flags are signed into the plan. Preparation, preview, revalidation and application use the same selected document projection; excluded confidential names and hashes must not leak through unrelated catalog entries. Current principal scope/tenant/review checks remain authoritative and a different visibility boundary can require regeneration. No model is called and historical knowledge is not captured as a new independent source.

Use the existing Wiki plan signature, immutable input hashes, expected revisions, transaction and dependent-page propagation. Add a merge plan kind, not a new persistent page schema or database. Recheck current support and historical time limits during preview/apply; apply fails when stale or unavailable. The target's existing originHash binds successful application to this exact signed plan for identical retry, without rewriting history; append an opaque commit reference in the existing log. Edits or new compilation invalidate that marker normally.

Preparing may initialize local proof state but never changes canonical pages, sources or Git commits. Applying needs a separate explicit review operation. Respect operation cancellation, reader/writer locking, ready-commit completion and recovery. A proposal returned after lock cleanup must still pass cancellation and time checks; all canonical mutations occur only inside the existing atomic writer transaction. Use synthetic documents, both Git defaults, exact Node20/22 installed consumers and independent read-only committed-candidate review.
