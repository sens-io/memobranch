# MemoBranch 竞品调研与功能增强建议

调研日期：2026-10-20。项目基线：`sens-io/memobranch`，分支 `codex/web-management`，提交 `9e29c0778919dcb45cb2de379b500e2bc72d0e60`。

## 结论

建议把 MemoBranch 做成“不同 Agent 都能使用、每次知识变化都有证据可查的本地 Wiki”。下一阶段优先改善接入、审核和效果验证，再扩展时间查询、资料接入和多人协作。

Git、Markdown 和文件式记忆仍然值得坚持，但已经不足以单独构成产品区别。Letta 当前的 MemFS 已把记忆放进 Git 仓库，支持分层文件、后台整理和共享仓库；OpenViking 也提供文件式上下文与 Wiki 编译。MemoBranch 更值得强化的是原始证据、明确审批、来源限制传播、可恢复写入，以及这些能力在不同 Agent 中保持一致。[Letta MemFS](https://docs.letta.com/concepts/memfs)、[OpenViking 编译说明](https://docs.openviking.ai/en/context-compilation/01-overview)。

这份报告比较的是公开能力和本地源码。没有安装运行全部竞品，也没有独立复现它们的效果、延迟或成本宣传。功能优先级是产品判断，仍需要实际使用反馈验证。

选择覆盖了记忆服务、带记忆的 Agent、文件式知识库和持续整理知识四种方案。下列 GitHub 星标是调研时公开页面的约数，只用于说明关注度，不能当市场占有率、用户数或质量排名。部分 GitHub API 请求受到限流，未成功的数字使用公开仓库页面，不假装全部来自实时 API。

## 二、MemoBranch 已有的东西，别再当新功能做

| 当前能力 | 本地依据 | 真正可以增强的部分 |
| --- | --- | --- |
| 原始证据、候选、审批、冲突、撤回、加密和恢复 | `src/vault.ts`、`src/transaction.ts`、`src/encryption.ts` 与现有回归 | 更便于理解的纠正和审核过程；保留已有约束。 |
| 来源总结、实体、概念、综合、比较和查询成果页 | `src/wiki-types.ts`、`src/wiki.ts` | 大批资料任务、定向重新编译和变化解释，不是重新实现 Wiki。 |
| 目录导航、规则、只读查询、明确回存、结构与语义检查 | `docs/wiki.md`、`src/wiki.ts` | 自动提出维护建议、来源更新提醒、实际使用效果评测。 |
| 中文/英文检索、可选向量、链接扩展、常驻记忆 | `src/search.ts`、`MemoryVault.context()`（组装给 Agent 的记忆上下文的方法） | 按模型使用的文本单位预算分配内容；去重、保留完整引用、解释选择原因。当前主要按字符上限截取。 |
| CLI、MCP、DeepSeek Harness 插件及可导入的 TypeScript 包 | `src/cli.ts`、`src/mcp.ts`、`src/deepseek-harness.ts`、`package.json` | 现有能力主要供调用；补安装向导、宿主支持的自动调用和 Python/框架使用示例。 |
| 文本文件与标准输入捕获、来源地址 | CLI 的 `contentFrom()`（读取文本参数、文件或输入流的方法）及证据类型 | 当前文件输入不是 PDF 解析器；来源地址也不等于网页抓取或持续同步。 |
| Web 审核、规则和配置、运维、Git 历史 | `src/web.ts`、`src/web-ui.ts` | 新旧内容并排比较、修改原因、受影响页面、来源变化追踪。当前已逐页展示计划，但没有完整的新旧比较体验。 |
| 过期时间、修订、替代关系与 Git 历史 | `src/types.ts`、`src/wiki-types.ts` | 仍不等于按照事实实际生效时间查询；需要分别表达何时记录、何时有效。 |
| 定时恢复、过期处理、索引与同步 | `MaintenanceService`（后台维护服务）、`src/maintenance.ts` | 不等于已有后台语义整理任务、编译进度或经验学习。 |

本地核对使用 README、公开导出、上述源码和已保存验收记录。为确认自动调用和上下文组装，还使用了本次新建的 CodeGraph 索引；没有因为索引未标出测试关系就推断某段代码没有测试。

## 三、建议顺序与首版范围

“优先”表示值得先验证，不表示现在必须一次做完。成本按相对改动范围估计；尚未拆开发任务，不给未经验证的天数承诺。

| 顺序 | 功能 | 用户能获得什么 | 第一版做到哪里 | 相对成本 |
| --- | --- | --- | --- | --- |
| 第一批 1 | 接入向导与自动使用记忆 | 接好之后，新会话能直接用上上次已确认的信息，减少手工提醒 Agent 调工具。 | 优先支持现有 DeepSeek Harness，再选一个高需求客户端；检查模型和 vault，展示将修改的客户端配置，提供验证和卸载恢复。自动读取覆盖已批准普通记忆、Wiki 页面及其实际引用；自动采集默认形成证据/候选，不自动批准 Wiki。 | 中；受宿主扩展接口限制 |
| 第一批 2 | 新旧比较、纠正与检索解释 | 看懂“为什么记住、从哪来、哪里变了”，降低误批准风险。 | 在现有 Web 审核里展示前后版本、来源、条件、敏感级别与影响页；自然语言纠正生成新证据和待审核计划；解释结果被选中的依据。 | 中 |
| 第一批 3 | 可复现的效果评测与真实示例 | 知道记忆是否改善任务，而不只是接口能返回内容。 | 固定一组跨会话、跨来源、更新与撤回任务；比较无记忆、现有 MemoBranch、增强版本；记录答案正确性、引用、延迟、调用量、费用和人工纠正。 | 中 |
| 第二批 4 | 文本/网页批量导入与更新追踪 | 把现有项目文档变成 Wiki，不用逐条复制；资料变了能找到受影响页面。 | 先目录、Markdown、文本和用户明确指定的网页；来源版本、重复导入、进度、取消、重试；PDF 随后加入。GitHub 文档接入之后再验证 Notion/Drive 需求。 | 中到高 |
| 第二批 5 | 时间查询与过时提示 | 回答“上个月为什么这样做”“现在还有效吗”。 | 区分记录时间和事实生效时间；按日期筛选/查看历史；现行回答标明已知过时或待核实的支持关系。 | 中到高 |
| 第二批 6 | 带预算的上下文组装 | 在相同模型成本下保留更相关、更完整的信息。 | 分配稳定偏好、项目总结和检索证据的预算；先概览后详情，删除重复片段，保留完整引用；不足时明确提示，不在中途截断重要条件。 | 中 |
| 第三批 7 | Agent 私有记忆、共享资料库与知识合并审核 | 团队可复用知识，同时保留每个 Agent 的试验空间。 | 先固定版本的共享只读资料库；再做私有变更提交、合并预览和人工审批；按每个资料库原有身份过滤后组合结果。 | 高 |
| 第三批 8 | 从工具经历形成流程建议与技能导出 | 多次成功/失败积累成可验证的操作建议。 | 先记录情境、动作、结果与限制，形成有来源的流程候选；跨任务验证后允许明确导出技能文件。 | 高，需独立效果与权限验证 |

最小可验证的产品路径是：完成接入 → 自动读到已确认记忆和 Wiki → 捕获新证据 → 看懂拟议变化 → 批准 → 下一次任务正确复用并保留引用。先把这条路径做顺，再扩展资料连接器。

## 四、为什么这些方向值得做

### 1. 接入与自动使用：最直接改善首次体验

Mem0 提供框架和 SDK 接入路径；Hindsight 提供面向多种编程 Agent 的安装与自动采集方案；Supermemory 提供多个客户端插件。它们共同降低“记忆服务已经装了，但 Agent 没有使用它”的概率。[Mem0](https://github.com/mem0ai/mem0)、[Hindsight 接入](https://hindsight.vectorize.io/sdks/integrations/coding-agents)、[Supermemory 插件](https://github.com/supermemoryai/supermemory)。

建议先把现有 Harness 插件从“能调用工具”增强为“宿主确有接口时，在合适时机调用”。不支持自动触发的客户端仍通过 MCP 使用，不宣传所有宿主都能无感自动采集。配置写入前展示差异、备份原配置，卸载时只移除自己新增的部分。

验收例子：首次会话确认一个项目约定；重开会话后无需重复说明即可正确使用；跨资料问题应使用已批准 Wiki 页面作答并引用实际读取的版本，而非只验证普通记忆检索；关闭采集后不新增证据；客户端重试不会重复生成候选；任何自动采集都不提升调用者权限。

### 2. 把审核和纠正做得直观

MemoBranch 已经把拟议页面与正式知识分开，这是可继续发展的产品能力。下一步是帮助人快速看出新增、删除、冲突、条件变化以及来源是否可靠。Hindsight Cloud 的控制台能查看回答依据与检索过程，其开放接口文档也说明了总结更新追踪；MemOS 公开提供反馈纠正路径。[Hindsight Cloud 控制台](https://docs.hindsight.vectorize.io/cloud/memory-banks/)、[总结更新追踪](https://hindsight.vectorize.io/0.9/developer/api/mental-models)、[MemOS](https://github.com/MemTensor/MemOS)。

检索解释展示可核实的事实：采用了哪种搜索、匹配到哪些来源、引用哪个版本、是否过时、为何因权限或预算排除。不要把模型生成的一段“我为什么这样想”伪装为实际检索记录；不能向无权限用户泄露被排除记录的标题、内容或数量。

验收例子：用户纠正“现在部署改用 pnpm”；系统保留原话，显示拟修改页面和旧内容；别人先更新页面后，旧计划无法覆盖；旧来源仍可追溯。

### 3. 效果评测：补上现在无法回答的问题

现有 488 项功能测试、故障与权限回归证明了很多工程行为，但没有直接证明“Agent 因此少犯多少错”。竞品的公开分数可用于选择测试方向，不能代替同模型、同输入、同任务的实测。Mem0 也明确说明托管优化和开源实现可能得分不同。[Mem0 的说明](https://github.com/mem0ai/mem0)。

建议首版使用 30–50 个公开或合成任务，覆盖长期偏好、跨文档综合、新旧事实、冲突拒答、撤回、权限与失败经验。对相同任务分别测无记忆、现有实现、增强实现；能容纳全部资料时可加全文上下文作为对照。固定模型、提示词、检索与生成预算，记录运行成本。公开数据集可补充，但不要先把大规模榜单当开发目标。

初期最重要的判断是：关键任务是否改善，引用是否正确，撤回与越权案例是否全部保持正确；没有测量前，不宣传准确率或成本下降百分比。

### 4. 资料与异步任务：减少复制，同时处理真实变化

Supermemory 展示了资料连接器与解析的产品价值；OpenViking 的编译操作有任务状态、取消与重试规则。这些能力可用于改善 MemoBranch 现有同步调用式编译，而不改变其正式知识必须经过明确批准的设计。[Supermemory 资料接入](https://supermemory.ai/product/)、[接入与权限更新](https://supermemory.ai/blog/agent-memory-ingestion-connectors/)、[OpenViking 编译任务](https://docs.openviking.ai/en/context-compilation/01-overview)。

建议状态依次为：等待 → 读取资料 → 保存证据 → 生成计划 → 等待审核 → 已应用；读取/编译失败和取消分别记录。旧任务重试先查已完成阶段，不能重复导入或重复批准。来源更新追加新证据；来源删除或权限收紧后，先阻止相关内容进入回答，再处理派生知识的重新审核。

PDF 等二进制原文件、页码和正文提取结果需要明确关联。当前远端同步只接受受支持文件和普通 Markdown；新增附件必须设计独立存放、加密、备份及来源哈希，不把二进制直接塞进现有允许范围，也不拿解析正文冒充原文件字节。

### 5. 时间与预算：在现有数据和检索上增强

Graphiti 把事实变化和有效时间作为明确能力；Supermemory 区分稳定画像和近期状态。MemoBranch 已有过期、修订和常驻卡片，但还可以更清楚地表达“记录于十月、实际从九月生效”，并限制临时状态常驻多久。[Graphiti](https://github.com/getzep/graphiti)、[Supermemory 画像](https://supermemory.ai/product/)。

时间查询首先作用于已有事实、修订与来源；不要为了回答历史问题恢复已被擦除的密钥，当前权限仍约束历史读取。预算组装则以模型实际使用的文本单位为目标，给出可替换的计量方式和估算状态，先不要绑定单一模型供应商。

OpenViking 的摘要、概览、正文分层值得参考，但其当前检索文档说明使用全局向量搜索加可选重新排序，并不沿目录递归搜索；不应照搬旧文章中的机制解释。[上下文分层](https://docs.openviking.ai/en/concepts/03-context-layers)、[当前检索机制](https://docs.openviking.ai/en/concepts/07-retrieval)。

### 6. 真正做出 MemoBranch 名字里的“分支”

这是比普通关系图更有项目特色、但需要更谨慎实施的长期方向：Agent 可在自己的记忆副本中提出变更，另一 Agent 或人比较新旧知识、检查来源后再合入共享版本；任务也可读取某个固定知识版本，便于重现结果。

Letta 已有 Git 记忆、副本并行整理和云端共享仓库，因此不能把“有分支”宣传成独有。MemoBranch 可以尝试把“有来源约束的知识合并审核、跨宿主复用、可离线运行”做得更明确。[Letta MemFS](https://docs.letta.com/concepts/memfs)、[共享记忆的部署限制](https://docs.letta.com/concepts/shared-memory)。

现有 Git 操作主要围绕一个工作目录的当前状态，不能直接让多个记忆分支共用同一套缓存、密钥和恢复记录。先设计每个副本的状态隔离，再考虑并行写入；文本能合并，不代表事实、有效时间或权限可以自动合并。

## 五、分阶段验证建议

| 阶段 | 交付与依赖 | 如何判断有用 |
| --- | --- | --- |
| 第一步 | 一个宿主的接入向导、自动读取和候选采集、可理解的审核比较；同时做小型评测。 | 邀请 5–10 位自愿试用的开发者，记录从干净环境到第一次跨会话正确复用的时间、成功率与人工纠正；这些是拟议样本，不是当前用户数据。 |
| 第二步 | 在第一步确有重复使用之后，加入目录/网页批量任务、更新追踪与上下文预算。 | 资料更新后能发现受影响页面；同预算下任务不退化；成本、延迟和错误能归因到具体阶段。 |
| 第三步 | 出现真实团队需求后，增加共享只读知识版本，再试私有分支与合并审批。 | 两个 Agent 可使用各自私有知识，同时复用授权共享内容；冲突需要明确处理，旧任务可以重现引用版本。 |

测量建议：只在用户同意的本地记录接入是否成功、候选是否被接受、检索/编译耗时、调用量和费用估算；正文与秘密不进入默认统计。出现新越权、错误撤回或来源错误时，不扩大试用，先修复该问题。

没有现成的用户访谈、使用量、留存或真实模型效果基线，因此目前不能断言“接入一定比时间查询更重要”。上述顺序优先解决已能从代码观察到的手工步骤，并用试用数据验证；如果开发者持续抱怨资料导入，它应提前。

## 六、暂时不优先投入的功能

- 先做大量图形展示：有关系数据不代表用户需要复杂关系图。先把引用、来源、新旧比较和检索解释做清楚。
- 默认自动改写正式知识：会削弱目前的来源与审批设计。可以自动提出计划，正式写入继续服从已有权限和批准规则。
- 同时开发十几个连接器和全套多媒体：需要长期维护授权、同步、撤回、解析与成本。先验证一条资料路径。
- 重新造云端多租户数据库或图数据库：与当前本地文件和单资料库的设计不同，尚无已验证需求要求承担这些改动。
- 自动执行从经验导出的技能：流程知识与可执行能力应分别审核；先导出给人检查，并验证它能在其他任务上复用。

## 七、资料与方法边界

官方仓库与文档是功能描述的来源，性能和采用率宣传不视为独立验证。GitHub 星标没有使用量分母。当前开源仓库、托管产品、旧版文档和新迁移入口分别标注，避免把一种部署的功能写成所有部署都有。

本报告只参考功能与方法，不复制外部代码。若进入开发，再核对拟采用版本的许可证、宿主接口与兼容范围，并为新增能力写 OpenSpec 场景。

本次仅建立了用户确认的本地 CodeGraph 索引，并将生成目录和临时工作目录加入忽略。报告中的功能是建议，没有修改运行代码或完成这些功能的实现。

独立复核：另一 Agent 只读检查了报告、关键官方来源与直接影响建议的源码，未发现必须纠正的事实错误或把已有能力误判为缺失；建议已采纳，将自动使用记忆的首版验收明确扩展到“已批准 Wiki 页面及其实际引用”。复核未重测竞品性能，也未独立重查全部星标。
