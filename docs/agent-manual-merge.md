# Wiki revision and manual merge tools for agents

Development-source capability, not yet published to npm. Build the current branch and use its existing MCP server or DeepSeek Harness plugin. No new configuration, grant, database or vault migration is required. The host still owns the vault path, identity, permissions, keys and cancellation; none can be supplied as tool arguments.

## Read, prepare, inspect, approve

1. Read the vault history with `memory_history` and current authorized catalog with `memory_wiki_catalog`. These are vault commits, not this software repository's commits.
2. Call `memory_wiki_snapshot` with `{ "commit": "FULL_LOCAL_ANCESTOR_HASH", "pageKeys": ["entity:atlas"] }`. The result includes complete historical pages and dependencies, provenance, the current `authorityHead` and separate `currentRevision`. Select the requested page by key; array position does not identify the target. Use a second snapshot at `authorityHead` for a current full comparison. Reload if heads or revisions differ.
3. With explicit human direction, call `memory_wiki_merge_prepare` with the historical `fromCommit`, `pageKey`, `expectedRevision` actually read, manually authored `body` and `summary`, and optional `title`. The body is Markdown, not a serialized record or its generated source-link suffix. Chinese/emoji text is preserved. There is no `apply` flag and no model rewrite. The result is `{ plan, preview, comparison }`.
4. Inspect the complete comparison, restrictions, conditions, uncertainty, sources and every affected page. `memory_wiki_preview` accepts `{ "plan": ORIGINAL_PLAN }` and checks current inputs without applying. Only after explicit approval of that exact reviewed content, call the separate `memory_wiki_apply` with the unchanged plan and review authority. Preparation is not approval; an agent must not infer approval from a successful tool response.

Both adapters use the same tool names and strict core input validation. Snapshot requires read permission; preparation requires read and write; approval requires review. Harness hides tools missing these permissions; MCP retains its existing discoverable list and refuses unauthorized execution. Host policy decides whether an agent may call the approval tool. This change does not modify host approval settings or install automatic activity.

## Bounds, privacy and failure

- Snapshot uses a full lowercase 40/64-character local ancestor commit and 1–25 distinct keys of at most 200 characters. See the [revision restrictions](wiki-revision-views.md) for dependency, stored-byte, ancestry, schema and current-source checks. It does not checkout, fetch, import, create a worktree, call a model or change Git refs/index.
- Preparation uses the [manual merge restrictions](manual-wiki-merge.md): expected positive safe-integer revision, nonempty body up to 100000 characters, summary up to 2000 and optional title up to 300. Both versions' sources and stricter conditions/restrictions survive. No automatic conflict resolution or inference of truth is provided.
- Sensitive/secret reads require explicit `includeSensitive` / `includeSecret` plus current authority and available keys. Both tools reject extra arguments, including `root`, `signal`, identity, credentials and `apply`. Confidential content, titles and relationships may be returned as plaintext to the authorized host. Signing is not encryption; later withdrawal cannot recall copied output.
- Complete pretty-printed JSON text, including escaping into a text-result envelope, is limited to 16 MiB. Preparation additionally checks a complete resubmittable `memory_wiki_apply` envelope. Oversized results fail with `CONTENT_TOO_LARGE`, not truncated text or a partial plan. Host/model context limits may be lower; do not approve a plan when the host has truncated or omitted its review. These are result bounds, not a memory sandbox or a new general input limit for existing tools.
- Enclosing request cancellation is passed through the existing operation handling; Harness unload cancels and waits for its calls. There is no extra outer lock or new overall deadline. Core checks still occur after actual asynchronous cleanup. A cancelled waiting call removes only its own lock ticket.
- Changed current inputs, withdrawal or erased keys can invalidate an old read/plan. Reload and prepare again; never alter its signed fields. If apply returned an uncertain outcome, inspect vault history first. An explicit retry may resend the original plan to `memory_wiki_apply`; the core recognizes an exact completed retry without another commit. Ordinary preview may already reject successfully applied old inputs; do not invent a new plan as a retry. A cancellation after a completed commit can report that commit in its error details.

This is local same-vault review, not cross-account sharing, branch/private-vault import, an offline archive, as-known-at answering or evidence of historical model quality. Original source bodies and PDF encodings are not exported as new evidence. No push, npm publication or deployment is performed by these tools.
